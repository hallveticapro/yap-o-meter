## Executive Summary

Yap-o-Meter is a focused classroom web app with a clear primary experience: local microphone analysis drives a full-screen animated canvas visualizer. The strongest parts of the project are its simple single-page flow, local Web Audio API processing, persistent teacher settings, Docker/GitHub Actions deployment path, and no evidence of raw audio upload, recording, or analytics.

The biggest risks are mostly privacy, validation, and maintainability issues rather than production-breaking runtime defects. The app can auto-activate the microphone when prior browser permission is already granted, pause does not stop the media stream, TypeScript validation currently fails because backup files are included in the project, production HTML includes a third-party Replit banner script, and calibration is described as automatic but does not actually update settings.

Highest-value next work should be: make microphone start/stop states explicit, remove or exclude stale backup code so typecheck passes, add permission-denied and reduced-motion/display modes, and add basic tests around audio calculations, cleanup, settings persistence, and accessibility.

## Architecture Overview

- Framework: React 18 + TypeScript single-page client, built by Vite.
- Routing: Wouter routes `/` to `VoiceMeter`; unmatched routes render a generic `NotFound`.
- State management: React hooks and component state. Teacher settings persist through `useLocalStorage`.
- Audio processing model: `useMicrophone` calls `navigator.mediaDevices.getUserMedia({ audio: true })`, creates an `AudioContext`, connects a `MediaStreamAudioSourceNode` to an `AnalyserNode`, reads frequency data in a requestAnimationFrame loop, and derives a 0-100 volume level locally.
- Data persistence: `voice-meter-settings` is persisted in `localStorage`; live volume is in memory. No raw audio recording, storage, or upload path was found.
- API/backend behavior: Express exists, but `server/routes.ts` registers no app routes. `server/storage.ts` and `shared/schema.ts` are scaffolded user/auth/database code and are not used by the visible app flow.
- Build/deployment model: `npm run build` runs Vite and bundles `server/index.ts`. Docker builds the frontend and `server/production.ts`; GitHub Actions runs `npm ci`, `npm test --if-present`, `npm run build`, then builds/pushes a GHCR image.
- Major user flows: permission overlay, live visualizer, status panel, pause/resume visual feedback, calibration button, settings sidebar, theme/threshold/sensitivity/alert controls, click/touch particle effects.

## Strengths

- Microphone access is presented through a clear overlay button on first use (`client/src/components/permission-overlay.tsx:19-24`).
- Media tracks and the primary AudioContext are stopped/closed on hook unmount (`client/src/hooks/use-microphone.ts:129-140`).
- Teacher settings persist locally without requiring accounts or server storage (`client/src/pages/voice-meter.tsx:31-33`, `client/src/hooks/use-local-storage.ts:7-21`).

- Docker and GitHub Actions provide a credible production build/deployment path.

- Severity: High

#### HIGH-003 Previously granted microphone permission can auto-activate on page load

- Severity: High
- Category: Privacy, Microphone Permissions, Classroom UX
- Location: `client/src/hooks/use-microphone.ts:112-127`
- Evidence: On mount, the hook queries microphone permission, and if the state is `granted`, it immediately calls `requestPermission()`, which opens `getUserMedia` and starts monitoring (`client/src/hooks/use-microphone.ts:17-35`).
- Impact: A teacher who previously granted permission may revisit the app and have the microphone turn on without a fresh in-app click. This is probably allowed by the browser, but it is surprising for a classroom microphone tool and conflicts with the safest "explicit user action" rule.
- Recommendation: Require an explicit "Start microphone" action for each session, or make auto-start a clearly labeled product decision with visible status and a stop control.
- Suggested priority: Immediate

## Voice Meter-Specific Audit Notes

### Microphone Permission Flow

First-time permission is requested through `PermissionOverlay` after clicking "Allow Microphone Access". Denial is caught and leaves `isPermissionGranted` false, which keeps the overlay visible. There is no distinct denied state or recovery guidance; the same overlay remains. If the browser permission was previously granted, `useMicrophone` auto-starts capture on mount.

### Audio Processing and Data Handling

Audio processing is local in the browser. `getUserMedia` feeds a Web Audio analyser, and only derived volume state is used for UI. No `MediaRecorder`, raw audio upload, remote audio endpoint, analytics call, or volume persistence path was found. Settings are persisted in `localStorage`; live volume and calibration samples are in memory. Calibration currently logs an aggregate average background-noise value.

### Media Stream Cleanup

On unmount, the microphone hook cancels the volume rAF loop, stops all stream tracks, and closes the primary AudioContext. Timeouts in the page are cleared on unmount. The canvas removes its resize listener and cancels its rAF on cleanup. Missing pieces: there is no manual stop control, pause does not stop tracks, alert AudioContexts are not closed, and hidden-tab/suspended-context handling is not explicit.

### Browser and Device Compatibility

The code accounts for `webkitAudioContext`, which helps Safari compatibility. The Permissions API query may fail on browsers that do not support querying microphone permission; this is caught with a warning. There is no teacher-facing unsupported-browser message for missing `navigator.mediaDevices`, no iOS Safari-specific manual checklist, and the build warned that Browserslist/caniuse-lite data is stale.

### Animation and Rendering Performance

The app renders 120 particles and uses offscreen emoji caching for emoji themes, which is a good optimization. The canvas loop currently restarts when volume state changes, and alert sounds create fresh AudioContexts. Continuous animation has no reduced-motion path. These are likely to matter most during long projected sessions on tablets, Chromebooks, or smartboards.

### Classroom Display Usability

The full-screen visualizer is understandable and engaging from a distance, and the auto-hiding status panel helps reduce clutter. Teacher controls remain accessible on the projected surface through the settings button/sidebar, and there is no fullscreen/display-only mode. Threshold and sensitivity are configurable, but calibration behavior is unclear because it does not update settings.
